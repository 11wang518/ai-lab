## 2026-10-11（下午）：把 YOLO 这半跑通

### 目标

上午只做完了大模型那半，YOLO 只有代码没跑过。这一节把它补上：
真正完成一次 ultralytics 训练，并把权重接进应用。

### 一路上卡了四次

**第一次：装不上 ultralytics（已解决）**

`pip install ultralytics` 一开始在本机沙箱里跑不通，后来加权限走通了。
装完发现是 **CPU 版 torch**（`2.14.1+cpu`），因为 PyPI 默认给的就是 CPU 版。

**第二次：GitHub 完全访问不了（改了方案）**

想要预训练权重和官方样例数据 `coco8`，两者都在 GitHub 上：

```
ssl.SSLCertVerificationError: unable to get local issuer certificate
```

用 `curl` 试也是 SSL 错误。于是换思路：**不用预训练权重，从零训练；不用官方数据集，自己生成。**
写了一个 `tools/make_synthetic_dataset.py`，用纯标准库画出 75 张图（车、人、路面、楼房），
标注在画图时直接算出来，不需要人工标。

**第三次：CUDA 版 torch 下不动（妥协了）**

CPU 训练太慢，想换成 CUDA 版。官方源 2.6 GB 的轮子下载速度只有 **0.65 MB/s**，
还多次连接超时；换国内镜像（阿里云 pytorch-wheels）连接是稳的，但速度依然是 0.65 MB/s，
估算要一个多小时。

权衡之后决定：**先走 CPU 把流程跑通**。这个数据集只有 75 张图，CPU 训练 5 分钟就够，
没必要为了一次实验等一小时。显卡升级的完整命令写在 `tools/check_gpu.py` 的提示里。

**第四次：沙箱挡住了训练进程（绕过）**

第一次训练启动时报了两个和代码无关的错：

1. matplotlib 想往 `C:\Users\...\AppData\Local\matplotlib` 写缓存，被拒绝；
2. ultralytics 建多进程管道时 `PermissionError: [WinError 5]`。

修法是把缓存目录改到项目内（`app/env_setup.py` 统一设置 `YOLO_CONFIG_DIR`
和 `MPLCONFIGDIR`，并把这两个目录加进 `.gitignore`），然后在沙箱外执行训练。

### 结果

```
模型      YOLO11n（2,590,230 参数，6.5 GFLOPs）
数据集    75 张合成图（60 训练 / 15 验证），181 个标注框
训练      100 epochs，imgsz 320，batch 8，CPU，耗时约 5.2 分钟
mAP50     0.995
mAP50-95  0.860
推理      8.5 ms / 张（CPU）
```

中间有一次对比很值得记：**30 轮的版本 mAP50 也有 0.888，看着不错，
但置信度普遍只有 0.1 左右，实际用起来几乎检不出东西。**
加到 100 轮后指标和置信度才同时正常。这件事说明：**不能只看 mAP，还要看置信度分布。**

### 接进应用

```powershell
python tools\start_background.py --provider ollama --model qwen2.5:1.5b ^
  --vision-backend ultralytics ^
  --vision-weights runs\train\synthetic-cpu\weights\best.pt --vision-conf 0.45
```

界面检测面板的右上角从"未加载"变成 `ultralytics`，示例图上的 3 辆车和 1 个行人
全部被正确框出（置信度 0.88 / 0.86 / 0.79 / 0.64）。

### 已知问题

同一个目标偶尔会被框两次（整体一个框、车身又一个框）。验证集指标看不出来，
因为重复框占比很小。现在的应对是把置信度阈值提到 0.45 压掉低分的那个。
要根治得换更真实的数据集重训。**这个限制写进了 `docs/YOLO训练记录.md`，
不打算藏着——被老师问到比主动说出来要难堪。**

### 下一步

1. 换真实数据集（COCO 子集 / VOC / 自己标的数据）重训一次，指标才有说服力；
2. 网络条件好的时候换成 CUDA 版 torch，把训练切到 4060 上；
3. 试一次导出 ONNX，比较一下 CPU 推理速度有没有提升。

## 2026-10-11：接上真实的 Ollama 模型

### 目标

把内置示例模型换成真实的本地大模型，并用实测数据验证，而不是"应该能用"。

### 完成的事

装好 Ollama 后拉了 `qwen2.5:1.5b`（Q4_K_M，986 MB）。先在 `ollama list`
里确认模型在，再用两个接口验证它真的在服务：

```
GET  http://127.0.0.1:11434/api/tags    → 列出模型，确认 capabilities 含 completion
GET  http://127.0.0.1:11434/api/ps      → 确认运行时占用
```

然后把应用切到 Ollama 后端：

```powershell
python run_server.py --provider ollama --model qwen2.5:1.5b
```

界面顶栏的状态点变绿，显示 `Ollama 本地模型 · qwen2.5:1.5b`，
说明应用和模型接上了。

### 实测数据

| 指标 | 实测值 |
| --- | --- |
| 模型文件大小 | 986 MB |
| 运行时显存占用 | 1166 MB（全部在 GPU 上） |
| 首 token 延迟 | 41 ms |
| 生成速度 | 约 299 字/秒，折算约 194 token/s |

8 GB 显存只用了约 1.1 GB，余量足够，和之前按参数量做的估算基本吻合。

### 新加的自检脚本

写了一个 `tools/check_llm.py`，一次跑两遍：

1. 直接连模型后端（`ollama` 的 `/api/chat`），测延迟和速度；
2. 再通过应用自己的 `/api/chat` 测一遍，确认前后端链路是通的。

**这个脚本当场就抓到一个 bug**：我一开始统计回答长度时，把 SSE 的 `done`
事件也算进去了，而 `done` 里带的是完整回答，结果长度被算成了两倍——
同一句话在输出里出现了两次。改成只累加 `delta` 事件才对。

另一个修正：最初按"1 个汉字 ≈ 1.5 个 token"折算速度，算出来 500 多 token/s，
明显不合理。千问的分词器对中文更省，系数接近 0.65，而且更稳妥的做法是
直接报"字/秒"，token 数只作为参考。**宁可报一个能解释的数，也不要报一个好看但站不住的数。**

### 卡住的地方

重启服务时遇到两个环境问题，都不是代码问题：

1. 上一轮启动的服务进程结束不了，报"拒绝访问"，最后用管理员权限 `taskkill` 才杀掉；
2. 默认的 PowerShell 外壳突然启动失败（`CreateProcessAsUserW failed: 5`），
   换成 cmd 外壳继续，不影响开发。

这类问题都写在这里，别人遇到同样报错时能少走弯路。

### 又踩了一个坑：服务"莫名其妙"消失

把服务留在后台过一段时间后，浏览器再打开就提示打不开了。查下来是
之前那个进程已经不在了（8000 端口没有监听），不是页面或代码的问题。

原因是"在终端里跑服务"这种方式本身就脆弱：终端一关、或者进程跟着终端一起被回收，
服务就没了，而界面上只表现为"打不开"，很容易误以为是程序写错了。

解决办法有两个，都已经放进仓库：

1. 根目录加了 `start-server.cmd`，双击就能启动，窗口里能直接看到日志；
2. `tools/start_background.py` 用独立进程把服务放到后台，日志写到临时目录，
   配套的 `tools/stop_background.py` 按端口找进程停止，不会误杀别的程序。

另外记一个实测细节：Ollama 空闲 5 分钟会把模型从显存卸掉，
所以间隔一段时间后的第一次提问首 token 要等约 2 秒（模型重新加载），
连续提问只要几十毫秒。文档里已经把这个区别标出来了。

### 下一步

1. 装 `ultralytics`，用公开数据集（比如 COCO 的子集或自己标的小数据集）真正跑一次训练；
2. 把训练出的 `best.pt` 通过 `yolo/serve.py` 接进来，替换掉现在的浏览器端降级演示；
3. 把这两个实测结果补进实验报告，并附上截图。

## 2026-10-10：从零搭起可运行的骨架

### 目标

作业要求两件事：本地大模型接入应用、YOLO 训练并实时接入应用。
先把"能跑起来的骨架"立起来，再往里填真模型。

### 环境摸底

先确认手里有什么，避免照搬别人的方案：

| 项目 | 结果 |
| --- | --- |
| 显卡 | NVIDIA GeForce RTX 4060，8 GB 显存 |
| Python | 3.13.3 |
| Node.js | v24.21.0（留给 Electron 用） |
| 已装的相关包 | 只有 `python-docx`，没有 torch / ultralytics / opencv |
| Ollama | 没装 |
| 网络 | pip 下不到包，PyPI 不可达 |

### 卡住的地方

**1. 装不了依赖（最主要的卡点）**

原本的计划是 `pip install ultralytics` 后直接训练。实际执行时：

```
ERROR: Could not find a version that satisfies the requirement fastapi (from versions: none)
```

网络受限，PyPI 拿不到包。torch 的 CUDA 轮子本身也要 2 GB 以上，就算能连上也很勉强。

**这个卡点直接决定了整个架构**：主应用必须做到零第三方依赖。
于是改用 Python 标准库写 HTTP 服务（`http.server`），不引入 FastAPI/Flask。
好处很实在：老师或同学拿到代码，`python run_server.py` 就能看到界面，
不会卡在装环境这一步；坏处是要自己写 multipart 解析和 SSE 分块输出，多花了点时间。

**2. 没有大模型服务**

Ollama 没装、LM Studio 没装，手上也没有任何权重文件。
如果应用只能连真模型，那今天连一张界面截图都拿不到。

解决办法是加一个 `DemoProvider`：规则匹配 + 流式输出，专门用来验证
"前端 → HTTP → SSE → 前端渲染"这条链路。它不做真实推理，界面上也明确标注了，
不会让人误以为这是模型的能力。

**3. 目标检测同理**

没有 ultralytics，检测接口只能返回"后端未就绪"。
为了不把链路留白，前端做了一层浏览器端降级：用 canvas 取像素、算局部对比度、
连通域找显著区域，结果在界面上标注为"启发式演示（非 YOLO）"。
**这一步的底线是不做假**：即使演示效果还行，也绝不把它当成 YOLO 的输出来展示。

**4. 开发过程中的两个真实 bug**

- 工具调用把 `12*(3+4)` 截成了 `12*(3+4`（正则要求以数字结尾，丢掉了右括号），
  导致计算器报语法错误。改成先宽松匹配、再按语法回退修剪，并把回退次数限制在 4 次以内，
  避免把残缺表达式"修"出一个错误答案。
- 发送按钮旁边的停止按钮在不该出现的时候显示了。原因是 `.icon-btn { display: inline-flex }`
  覆盖掉了浏览器默认的 `[hidden] { display: none }`。加了一条 `[hidden]` 的强制规则。

### 完成的事

- `app/`：配置、模型后端（demo/ollama/openai 兼容）、轻量智能体、检测后端、HTTP 服务、CLI
- `web/`：原生三件套前端，对话流式渲染 + 图片上传 + canvas 画框
- `yolo/`：训练、推理、实时、导出、独立推理服务五个脚本
- `desktop/`：Edge 应用模式（零依赖）和 Electron 两种桌面外壳
- `tools/`：示例图生成脚本、端到端冒烟测试
- `docs/`：这份日志、实现思路、部署与显存规划

### 验证结果

`python tools/smoke_test.py` 共 23 项检查，全部通过，覆盖：
健康检查、配置脱敏、静态资源、SSE 流式对话（39 个分片）、工具调用结果正确性
（`12*(3+4)=84`）、图片上传检测、以及空消息/未知后端/空图片三个错误分支。

界面用无头 Edge 截图确认过，两个面板的布局、状态点、检测框和结果列表都正常。

### 当时的想法

- **先把链路打通，再换真模型。** 反过来做的话，一旦模型环境出问题，
  根本分不清是接口写错了还是模型没起来。
- **诚实比好看重要。** 没有模型就说没有模型，降级演示要标清楚，
  不然答辩时被问一句"这是 YOLO 的输出吗"就说不清了。
- **解耦要留在配置里，不要留在代码里。** 换模型、换推理位置都只改环境变量，
  这样"本机跑"和"远程跑"只差一行配置。
