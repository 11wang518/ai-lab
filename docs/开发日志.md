## 2026-10-11（收尾）：找到"改了参数却不生效"的真正原因

### 现象

测试启动脚本时用 `netstat` 一看，**8000 端口上有两个进程同时在 LISTENING**：

```
TCP    127.0.0.1:8000     LISTENING    22160
TCP    127.0.0.1:8000     LISTENING    23764
```

两个服务都活着，请求会落到哪一个由系统决定。

### 原因

`LabServer` 里写了 `allow_reuse_address = True`。这一行在 Linux 上是常规操作
（避免重启时的 TIME_WAIT 问题），但在 **Windows 上它的语义完全不同**：
`SO_REUSEADDR` 允许两个进程绑同一个端口，而不是"稍后可以重用"。

**这解释了之前一次真实的困惑**：我明明用 `--vision-conf 0.45` 重启了服务，
查健康接口却显示 0.35——因为答复我的是另一个还活着的旧进程。
当时以为是启动脚本的问题，其实是端口被重复绑定了。

同一个原因还让 `find_free_port()` 不可靠：它自己先设了 `SO_REUSEADDR` 再试探绑定，
结果**已占用的端口也被判成"空闲"**，自动换端口的功能形同虚设。

### 修复

1. Windows 上关闭 `allow_reuse_address`，端口被占用时让绑定直接失败，
   而不是偷偷绑上去；
2. `find_free_port()` 在 Windows 上改用 `SO_EXCLUSIVEADDRUSE` 探测；
3. 端口占用时的报错从一串堆栈改成人话：

```
[启动失败] 端口 8000 无法绑定：[WinError 10048] ...
          可能已经有一个服务在跑，或者端口被别的程序占用。
          换一个端口试试：python run_server.py --port 8010
```

验证方式：先正常起一个服务，再用 `--no-fallback-port` 起第二个，
现在会稳定报错（修复前会"成功"绑上去）。

### 顺带修掉的启动脚本

`start-server.cmd` 双击后满屏报错。原因是文件是 **UTF-8 无 BOM，但 cmd 按 GBK 解析**，
中文的字节序列被拆成了命令名，连 `echo` 都执行不了。

改成**纯 ASCII 输出**（不再依赖代码页），并且用 `goto` 分支代替括号块
（括号块里的多行续行在 cmd 里很容易出问题）。
现在是英文提示，出错时会 `pause` 保留窗口。

> 教训：**给 Windows 写 .cmd，别在里面放非 ASCII 字符**。
> 中文说明写在 README 和 Markdown 文档里，那边是 UTF-8 环境，不会出问题。

## 2026-10-11（深夜二）：网页端也加上实时检测

### 为什么加

面试官明确要"实时推理"。命令行版 `realtime.py` 能跑、也有 49.5 FPS 的数据，
但现场演示要开终端、还得有摄像头或视频文件，不够稳。

网页端当时只能传静态图片——这在"实时"这个词面前站不住。所以补上：
**浏览器直接采摄像头画面，一帧一帧送去检测，框实时画在画面上。**

### 怎么做的

```
浏览器 getUserMedia 取画面
   → 画到离屏 canvas，缩到最长边 640，压成 JPEG(质量 0.7)
   → POST /api/detect
   → 拿回检测框，画到显示画布上
   → 立刻取下一帧
```

几个具体决定：

- **串行发送**（上一帧没回来就不发下一帧），避免请求堆积把内存吃满；
- **上传前缩到 640**：模型本来也会缩放，传大图纯属浪费带宽；
- 帧率显示的是"每秒完成多少次检测"，不是一个虚数。

页面上新增"摄像头实时"按钮，另外可以用 `?camera=1` 一步进入，方便现场演示。

### 性能

这个模式的瓶颈是一次往返。写了 `tools/bench_detect.py` 压测（模拟网页端的缩放和编码）：

| 指标 | 数值 |
| --- | --- |
| 平均往返 | **17.8 ms**（约 56 FPS 上限） |
| P50 / P95 | 16.4 ms / 32.6 ms |
| 上传体积 | 44 KB |

服务端不是瓶颈，实际帧率主要看浏览器截帧和编码的开销。

### 一个没能验证的地方（要如实说）

**无头浏览器不支持 `getUserMedia`**，权限回调不返回，页面会一直停在
"正在请求摄像头权限…"。我试了两次（包括加长虚拟时间预算），都卡在这一步，
所以**网页摄像头这一段我没法在本机自动化验证**。

页面按钮、状态提示、代码路径都检查过了，`node --check` 也确认脚本语法没问题，
但"真实摄像头下能不能跑"需要你自己开一次确认——这是目前唯一一个
只有"代码正确"没有"实测数据"的地方，我不想含糊过去。

### 顺手修的一个自己写的 bug

写 `startCamera()` 时，我把聊天那边的 `state.controller.abort()` 一起抄了过来。
那行会在打开摄像头的瞬间**中断正在进行的对话**。
虽然不影响检测功能，但属于明显的误伤，已经删掉。

### 下一步

1. 用真实摄像头确认网页实时模式（这是当前唯一待验证项）；
2. 如果现场网络不稳，可以改用 `yolo/serve.py` 把推理放本机、只暴露一个接口；
3. 数据集扩到几百张之后重训，把置信度提上来。

## 2026-10-11（深夜）：补上"实时推理部署"这一项

### 问题

回头看作业要求，"实时推理部署"这一条其实一直没真正跑过——
`yolo/realtime.py` 写好了，但从没执行过，也就没有 FPS 数据。
**脚本存在 ≠ 功能可用**，这一项必须实测。

### 没有摄像头怎么办

写了个 `tools/make_test_video.py`：把几张真实照片按轻微平移拼成一段 160 帧的
测试视频，用来在没有摄像头的情况下验证实时推理。

同时给 `realtime.py` 加了无窗口模式（`--no-show`），
因为服务器上没有显示器，`cv2.imshow` 会直接报错。
顺带加了 `--save`（把标注后的画面写成视频）和 `--max-frames`（限制处理帧数）。

### 结果

```
总帧数     : 160
总耗时     : 3.23 s
平均帧率   : 49.5 FPS
单帧推理   : 18.40 ms
```

带视频编码写文件时是 26.4 FPS，仍然满足实时（≥25 FPS）。

### 踩的坑

**第一次统计出了一个离谱的数字：1043 FPS。**

原因是我的 FPS 统计窗口每 0.5 秒把 `started` 重置了一次，
而最后算"总耗时"时用的还是同一个变量，于是总耗时变成了"最后一次重置到结束"的时间。
单帧推理 18.79 ms 才是真实值，一除就知道总耗时应该是 3 秒左右。

**教训：算平均值的时候，别和"滑动窗口"共用同一个计时变量。**
修完重新跑，49.5 FPS，和单帧耗时对得上。

另外 `half` 参数在新版 ultralytics 里已经弃用（提示改用 `quantize`），
每帧都刷一条警告。改成只在真的需要时才传这个参数，输出就干净了。

### 独立推理服务也验证了

`yolo/serve.py` 拉起后实测：

- `GET /health` → `{"ok": true, "classes": 80, "imgsz": 640, "conf": 0.25}`
- `POST /predict` → 同一张街景照片返回 12 个框，和进程内推理结果一致

这条路径的意义是把推理和应用解耦：显卡机器跑推理，应用可以放在别的地方。

### 下一步

1. 把真实数据集扩大到几百张，重训一次（现在的瓶颈只有数据）；
2. 试一次 ONNX 导出，对比导出前后的速度和精度；
3. 如果要写进简历，可以再加一个"多路视频并发"的压测。

## 2026-10-11（晚）：用真实数据微调，自有模型终于能认照片

### 目标

前面合成的数据和真实照片对不上，自己训的模型基本没用。这一轮要解决的是：
**让"我们自己训练的模型"也能认真实照片**，而不是只能靠官方预训练权重。

### 找数据

思路很明确：问题出在数据分布，那就换成真实数据。

先用 HuggingFace 镜像的搜索接口找带标注的真实数据集：

```
GET https://hf-mirror.com/api/datasets?search=coco8
```

找到 `cc92yy3344/coco8`——**已经是 YOLO 格式**（`images/` + `labels/` + `data.yaml`），
8 张真实照片、400 KB，正好用来验证微调流程。于是写了 `tools/fetch_coco8.py` 把它拉下来。

### 卡住的地方

**一、默认 User-Agent 被拦**

第一次下载每个文件都返回 `HTTP Error 403: Forbidden`。
换成 `curl` 请求同一个地址却是 200，说明是**请求头的问题**——镜像会拦掉
`python-urllib` 的默认 UA。加上一个正常的 User-Agent 就好了。

**二、镜像的网络会抖**

下载过程中出现 `getaddrinfo failed`（DNS 解析失败）和
`WinError 10054`（连接被远端重置）。这种是环境问题，不是代码问题，
所以给下载函数加了自动重试（最多 5 次、退避等待），一次就过了。

### 训练

```powershell
python yolo\train.py --data datasets\coco8\data.yaml --model yolo11n.pt ^
  --epochs 50 --imgsz 640 --batch 8 --device 0 --workers 4 --name coco8-ft
```

和前面唯一的不同是 `--model` 从 `yolo11n.yaml`（从零）换成 `yolo11n.pt`（预训练）。
日志里 `Transferred 499/499 items from pretrained weights`，说明 80 类权重全部继承。

39 轮早停（第 19 轮最佳），**GPU 上 25 秒**。

COCO8 验证集：**mAP50 0.872、mAP50-95 0.645**。

### 结果：目标达成了

拿那张真实街景照片分别测两个模型：

| 模型 | 检测结果 |
| --- | --- |
| 原始预训练 `yolo11n.pt` | 11 个目标，最高 car 0.87 |
| **自己微调的 `coco8-ft`** | 12 个目标，car 0.79 / car 0.78 / motorcycle 0.77 / person 0.60 |

**自己训练的模型现在能认真实照片了。** 应用也改成默认加载它
（`runs/train/coco8-ft/weights/best.pt`），界面上显示的就是自有模型的结果。

### 但是要说实话

微调后的置信度比预训练模型低一点（0.79 vs 0.87），框也略多。
原因不复杂：**只用了 4 张图训练**，模型会略微"过拟合"这几张。

所以结论不能吹：**"能认"和"好用"是两件事**。
能认，是因为换了真实数据、用对了迁移学习；好用，还需要几百到几千张真实数据。
这一点写进训练记录的局限章节了。

### 下一步

1. 把真实数据集扩到几百张以上（COCO 子集、VOC，或者自己标），指标才有说服力；
2. 试一次 ONNX 导出，比较导出前后的推理速度和精度；
3. 如果还要继续做，可以试试更大的模型（`yolo11s`）看 8 GB 显存够不够。

## 2026-10-11（傍晚）：换显卡训练，把示例图换成真实照片

### 目标

两件事：训练和推理改用 RTX 4060；应用里的示例图片换成真实照片。

### 卡住的地方

**一、清华镜像在这台机器上根本不通**

先按最省事的思路试清华镜像，结果是 DNS 解析失败（curl 报 `Couldn't resolve host`）：

| 镜像 | 结果 |
| --- | --- |
| `mirrors.tuna.tsinghua.edu.cn/pytorch-wheels/` | 解析失败 |
| `pypi.tuna.tsinghua.edu.cn` | 连不上（HTTP 000） |
| `mirror.sjtu.edu.cn` / `mirrors.ustc.edu.cn` | 解析失败 |
| `mirrors.aliyun.com/pytorch-wheels/` | **可用（HTTP 200）** |

所以最后用了阿里云的 PyTorch 镜像。魔搭社区能连，但没有现成的 torch wheel。

**二、单连接被限速到 0.9 MB/s**

CUDA 版 torch 的 wheel 是 2.6 GB，单连接实测 **0.94 MB/s**，要 46 分钟。
改成 6~8 个分片并发后能到 **4~6 MB/s**，15 分钟下载完成。

为此写了 `tools/fast_download.py`：多线程分段 + 断点续传 + 自动重试。
这不是过度设计——第一次下载时末尾有 3 个分片被服务器重置，文件少了 2.5%，
校验才发现。带续传之后第二次就完整了。

**三、两个小坑**

- 下载完的文件名必须符合 wheel 规范。我一开始存成 `torch-cu126.whl`，
  pip 直接拒绝：`is not a valid wheel filename`。改成
  `torch-2.14.1+cu126-cp313-cp313-win_amd64.whl` 才行。
- 用 `-f http://...` 指定镜像时要加 `--trusted-host`，否则 pip 会因为
  不是 HTTPS 而忽略这个源。

**四、预训练权重还在 GitHub 上**

AMP 自检需要下载模型文件，GitHub 依旧不通，日志提示自检被跳过。
训练还是照常跑完（实测没有 NaN、没有零 mAP）。

预训练权重最后是从 **HuggingFace 镜像 hf-mirror.com** 拿到的，这个域名在这台机器上可访问。

### 结果

同一套参数，只改 `--device`：

| 对比项 | CPU | GPU（RTX 4060） | 差异 |
| --- | --- | --- | --- |
| 100 轮训练 | 5.2 分钟 | **1.5 分钟** | 快 3.5 倍 |
| 单张推理 | 8.5 ms | **1.7 ms** | 快 5 倍 |
| mAP50 | 0.995 | 0.995 | 持平 |
| mAP50-95 | 0.860 | **0.869** | 略优 |
| 显存占用 | —— | 0.4 GB | 8 GB 的 5% |

### 换成真实照片后发现的真问题

把示例图从程序画的"卡通街景"换成真实照片之后，立刻暴露一个问题：

**自己训练的模型在真实照片上几乎什么都检不出来。**

原因不复杂——它只学过合成风格的车和人，换成真实照片就完全对不上。
这恰恰说明前面的 0.995 mAP 只在合成集上成立，不能当成真实场景的效果。

处理办法是分两条线，并在文档里写清楚各自的用途：

- **应用演示**用 COCO 预训练权重 `yolo11n.pt`（80 个真实类别），
  真实照片上能正确识别出车辆、电动车和行人；
- **自己训练的权重**用来证明训练流程跑通，只在合成风格图片上有效。

最终示例图用的是自己的街景照片（`web/samples/street.jpg`），
实测识别出 7 个目标：4 辆车、1 辆电动车、2 个人，其中最高置信度 0.87，
单张 22.6 ms。

### 顺带清理

- 删掉了程序生成示例图的 `tools/make_sample_image.py` 和那张卡通图，
  示例目录 `web/samples/` 现在只有真实照片；
- 过期的截图（合成效果图）一并删除，文档里只保留真实照片的效果图。

### 下一步

真正的下一步已经很清楚了：**把预训练权重放在真实数据集上微调一次**。
现在的状态是"训练流程验证过、真实检测靠预训练模型"，
离"用自己训练的模型检测真实场景"还差一个真实数据集。

## 2026-10-11（下午）：把 YOLO 这半跑通

### 目标

上午只做完了大模型那半，YOLO 只有代码没跑过。这一节把它补上：
真正完成一次 ultralytics 训练，并把权重接进应用。

### 一路上卡了四次

**第一次：装不上 ultralytics（已解决）**

`pip install ultralytics` 一开始在本机沙箱里跑不通，后来加权限走通了。
装完发现是 **CPU 版 torch**（`2.14.1+cpu`），因为 PyPI 默认给的就是 CPU 版。

**第二次：GitHub 完全访问不了（改了方案）**

想要预训练权重和官方样例数据 `coco8`，两者都在 GitHub 上：

```
ssl.SSLCertVerificationError: unable to get local issuer certificate
```

用 `curl` 试也是 SSL 错误。于是换思路：**不用预训练权重，从零训练；不用官方数据集，自己生成。**
写了一个 `tools/make_synthetic_dataset.py`，用纯标准库画出 75 张图（车、人、路面、楼房），
标注在画图时直接算出来，不需要人工标。

**第三次：CUDA 版 torch 下不动（妥协了）**

CPU 训练太慢，想换成 CUDA 版。官方源 2.6 GB 的轮子下载速度只有 **0.65 MB/s**，
还多次连接超时；换国内镜像（阿里云 pytorch-wheels）连接是稳的，但速度依然是 0.65 MB/s，
估算要一个多小时。

权衡之后决定：**先走 CPU 把流程跑通**。这个数据集只有 75 张图，CPU 训练 5 分钟就够，
没必要为了一次实验等一小时。显卡升级的完整命令写在 `tools/check_gpu.py` 的提示里。

**第四次：沙箱挡住了训练进程（绕过）**

第一次训练启动时报了两个和代码无关的错：

1. matplotlib 想往 `C:\Users\...\AppData\Local\matplotlib` 写缓存，被拒绝；
2. ultralytics 建多进程管道时 `PermissionError: [WinError 5]`。

修法是把缓存目录改到项目内（`app/env_setup.py` 统一设置 `YOLO_CONFIG_DIR`
和 `MPLCONFIGDIR`，并把这两个目录加进 `.gitignore`），然后在沙箱外执行训练。

### 结果

```
模型      YOLO11n（2,590,230 参数，6.5 GFLOPs）
数据集    75 张合成图（60 训练 / 15 验证），181 个标注框
训练      100 epochs，imgsz 320，batch 8，CPU，耗时约 5.2 分钟
mAP50     0.995
mAP50-95  0.860
推理      8.5 ms / 张（CPU）
```

中间有一次对比很值得记：**30 轮的版本 mAP50 也有 0.888，看着不错，
但置信度普遍只有 0.1 左右，实际用起来几乎检不出东西。**
加到 100 轮后指标和置信度才同时正常。这件事说明：**不能只看 mAP，还要看置信度分布。**

### 接进应用

```powershell
python tools\start_background.py --provider ollama --model qwen2.5:1.5b ^
  --vision-backend ultralytics ^
  --vision-weights runs\train\synthetic-cpu\weights\best.pt --vision-conf 0.45
```

界面检测面板的右上角从"未加载"变成 `ultralytics`，示例图上的 3 辆车和 1 个行人
全部被正确框出（置信度 0.88 / 0.86 / 0.79 / 0.64）。

### 已知问题

同一个目标偶尔会被框两次（整体一个框、车身又一个框）。验证集指标看不出来，
因为重复框占比很小。现在的应对是把置信度阈值提到 0.45 压掉低分的那个。

## 2026-10-11：接上真实的 Ollama 模型

### 目标

把内置示例模型换成真实的本地大模型，并用实测数据验证，而不是"应该能用"。

### 完成的事

装好 Ollama 后拉了 `qwen2.5:1.5b`（Q4_K_M，986 MB）。先在 `ollama list`
里确认模型在，再用两个接口验证它真的在服务：

```
GET  http://127.0.0.1:11434/api/tags    → 列出模型，确认 capabilities 含 completion
GET  http://127.0.0.1:11434/api/ps      → 确认运行时占用
```

然后把应用切到 Ollama 后端：

```powershell
python run_server.py --provider ollama --model qwen2.5:1.5b
```

界面顶栏的状态点变绿，显示 `Ollama 本地模型 · qwen2.5:1.5b`，
说明应用和模型接上了。

### 实测数据

| 指标 | 实测值 |
| --- | --- |
| 模型文件大小 | 986 MB |
| 运行时显存占用 | 1166 MB（全部在 GPU 上） |
| 首 token 延迟 | 41 ms |
| 生成速度 | 约 299 字/秒，折算约 194 token/s |

8 GB 显存只用了约 1.1 GB，余量足够，和之前按参数量做的估算基本吻合。

### 新加的自检脚本

写了一个 `tools/check_llm.py`，一次跑两遍：

1. 直接连模型后端（`ollama` 的 `/api/chat`），测延迟和速度；
2. 再通过应用自己的 `/api/chat` 测一遍，确认前后端链路是通的。

**这个脚本当场就抓到一个 bug**：我一开始统计回答长度时，把 SSE 的 `done`
事件也算进去了，而 `done` 里带的是完整回答，结果长度被算成了两倍——
同一句话在输出里出现了两次。改成只累加 `delta` 事件才对。

另一个修正：最初按"1 个汉字 ≈ 1.5 个 token"折算速度，算出来 500 多 token/s，
明显不合理。千问的分词器对中文更省，系数接近 0.65，而且更稳妥的做法是
直接报"字/秒"，token 数只作为参考。**宁可报一个能解释的数，也不要报一个好看但站不住的数。**

### 卡住的地方

重启服务时遇到两个环境问题，都不是代码问题：

1. 上一轮启动的服务进程结束不了，报"拒绝访问"，最后用管理员权限 `taskkill` 才杀掉；
2. 默认的 PowerShell 外壳突然启动失败（`CreateProcessAsUserW failed: 5`），
   换成 cmd 外壳继续，不影响开发。

这类问题都写在这里，别人遇到同样报错时能少走弯路。

### 又踩了一个坑：服务"莫名其妙"消失

把服务留在后台过一段时间后，浏览器再打开就提示打不开了。查下来是
之前那个进程已经不在了（8000 端口没有监听），不是页面或代码的问题。

原因是"在终端里跑服务"这种方式本身就脆弱：终端一关、或者进程跟着终端一起被回收，
服务就没了，而界面上只表现为"打不开"，很容易误以为是程序写错了。

解决办法有两个，都已经放进仓库：

1. 根目录加了 `start-server.cmd`，双击就能启动，窗口里能直接看到日志；
2. `tools/start_background.py` 用独立进程把服务放到后台，日志写到临时目录，
   配套的 `tools/stop_background.py` 按端口找进程停止，不会误杀别的程序。

另外记一个实测细节：Ollama 空闲 5 分钟会把模型从显存卸掉，
所以间隔一段时间后的第一次提问首 token 要等约 2 秒（模型重新加载），
连续提问只要几十毫秒。文档里已经把这个区别标出来了。

### 下一步

1. 装 `ultralytics`，用公开数据集（比如 COCO 的子集或自己标的小数据集）真正跑一次训练；
2. 把训练出的 `best.pt` 通过 `yolo/serve.py` 接进来，替换掉现在的浏览器端降级演示；
3. 把这两个实测结果补进实验报告，并附上截图。

## 2026-10-10：从零搭起可运行的骨架

### 目标

作业要求两件事：本地大模型接入应用、YOLO 训练并实时接入应用。
先把"能跑起来的骨架"立起来，再往里填真模型。

### 环境摸底

先确认手里有什么，避免照搬别人的方案：

| 项目 | 结果 |
| --- | --- |
| 显卡 | NVIDIA GeForce RTX 4060，8 GB 显存 |
| Python | 3.13.3 |
| Node.js | v24.21.0（留给 Electron 用） |
| 已装的相关包 | 只有 `python-docx`，没有 torch / ultralytics / opencv |
| Ollama | 没装 |
| 网络 | pip 下不到包，PyPI 不可达 |

### 卡住的地方

**1. 装不了依赖（最主要的卡点）**

原本的计划是 `pip install ultralytics` 后直接训练。实际执行时：

```
ERROR: Could not find a version that satisfies the requirement fastapi (from versions: none)
```

网络受限，PyPI 拿不到包。torch 的 CUDA 轮子本身也要 2 GB 以上，就算能连上也很勉强。

**这个卡点直接决定了整个架构**：主应用必须做到零第三方依赖。
于是改用 Python 标准库写 HTTP 服务（`http.server`），不引入 FastAPI/Flask。
好处很实在：老师或同学拿到代码，`python run_server.py` 就能看到界面，
不会卡在装环境这一步；坏处是要自己写 multipart 解析和 SSE 分块输出，多花了点时间。

**2. 没有大模型服务**

Ollama 没装、LM Studio 没装，手上也没有任何权重文件。
如果应用只能连真模型，那今天连一张界面截图都拿不到。

解决办法是加一个 `DemoProvider`：规则匹配 + 流式输出，专门用来验证
"前端 → HTTP → SSE → 前端渲染"这条链路。它不做真实推理，界面上也明确标注了，
不会让人误以为这是模型的能力。

**3. 目标检测同理**

没有 ultralytics，检测接口只能返回"后端未就绪"。
为了不把链路留白，前端做了一层浏览器端降级：用 canvas 取像素、算局部对比度、
连通域找显著区域，结果在界面上标注为"启发式演示（非 YOLO）"。
**这一步的底线是不做假**：即使演示效果还行，也绝不把它当成 YOLO 的输出来展示。

**4. 开发过程中的两个真实 bug**

- 工具调用把 `12*(3+4)` 截成了 `12*(3+4`（正则要求以数字结尾，丢掉了右括号），
  导致计算器报语法错误。改成先宽松匹配、再按语法回退修剪，并把回退次数限制在 4 次以内，
  避免把残缺表达式"修"出一个错误答案。
- 发送按钮旁边的停止按钮在不该出现的时候显示了。原因是 `.icon-btn { display: inline-flex }`
  覆盖掉了浏览器默认的 `[hidden] { display: none }`。加了一条 `[hidden]` 的强制规则。

### 完成的事

- `app/`：配置、模型后端（demo/ollama/openai 兼容）、轻量智能体、检测后端、HTTP 服务、CLI
- `web/`：原生三件套前端，对话流式渲染 + 图片上传 + canvas 画框
- `yolo/`：训练、推理、实时、导出、独立推理服务五个脚本
- `desktop/`：Edge 应用模式（零依赖）和 Electron 两种桌面外壳
- `tools/`：示例图生成脚本、端到端冒烟测试
- `docs/`：这份日志、实现思路、部署与显存规划

### 验证结果

`python tools/smoke_test.py` 共 23 项检查，全部通过，覆盖：
健康检查、配置脱敏、静态资源、SSE 流式对话（39 个分片）、工具调用结果正确性
（`12*(3+4)=84`）、图片上传检测、以及空消息/未知后端/空图片三个错误分支。

界面用无头 Edge 截图确认过，两个面板的布局、状态点、检测框和结果列表都正常。

### 当时的想法

- **先把链路打通，再换真模型。** 反过来做的话，一旦模型环境出问题，
  根本分不清是接口写错了还是模型没起来。
- **诚实比好看重要。** 没有模型就说没有模型，降级演示要标清楚，
  不然答辩时被问一句"这是 YOLO 的输出吗"就说不清了。
- **解耦要留在配置里，不要留在代码里。** 换模型、换推理位置都只改环境变量，
  这样"本机跑"和"远程跑"只差一行配置。
