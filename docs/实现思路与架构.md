# 实现思路

这份文档不解释每一行代码，只讲**为什么这么做**。代码细节看源码和注释。

---

## 一、先想清楚一件事：这个项目到底有几个"会变的部件"

作业里只有两个功能，但真正会变的东西有四个：

1. 用哪个大模型（Ollama / LM Studio / llama.cpp / 云端平台）；
2. 模型跑在哪台机器上（本机显卡 / 另一台机器）；
3. YOLO 用什么权重、什么后端（ultralytics / ONNX / TensorRT）；
4. 应用长什么样（CLI / Web / 桌面）。

如果把这四件事写死在一起，后面每换一样都要动全项目。
所以第一个决定是：**按"会变的东西"切边界**，而不是按技术栈切。

```
┌──────────────────────────────────────────────┐
│ 界面层   CLI  |  Web  |  桌面壳               │
├──────────────────────────────────────────────┤
│ 协议层   HTTP + JSON + SSE                    │  ← 唯一的固定接口
├──────────────────────────────────────────────┤
│ 能力层   对话服务  |  检测服务  |  智能体      │
├──────────────────────────────────────────────┤
│ 后端层   模型后端可插拔   检测后端可插拔        │
└──────────────────────────────────────────────┘
```

界面层只认 HTTP，能力层只认抽象接口，后端层负责对接真实实现。
换模型、换推理位置都发生在最底下那一层，上面三层不用改。

## 二、为什么让主应用"零依赖"

这是被现实逼出来的决定，不是洁癖。

准备环境时发现 pip 装不了包。如果主应用依赖 FastAPI，那么"打开就能看"就变成
"先想办法装上 FastAPI"，而对方的环境可能比我这台还受限。

改成标准库之后，代价是自己实现三件事：

| 需求 | 标准库方案 | 代价 |
| --- | --- | --- |
| HTTP 服务 | `http.server.ThreadingHTTPServer` | 路由要手写 |
| 流式输出 | 手动写 chunked 分块 + `text/event-stream` | 要处理客户端提前断开 |
| 图片上传 | 自己解析 `multipart/form-data` | 约 50 行，够用 |

换来的是：`python run_server.py` 一条命令，任何装了 Python 的机器都能跑起来演示。
对一份要交给别人复现的作业来说，这个交换是值的。

**注意边界**：零依赖只约束主应用。YOLO 那边该装 ultralytics 就装，
不为了"零依赖"去手写一个检测器，那是南辕北辙。

## 三、大模型接入：一张表决定一切

三种后端，实际只有两类协议：

| 后端 | 协议 | 说明 |
| --- | --- | --- |
| Ollama | `/api/chat`，NDJSON 流 | 自己的一套，单独写 |
| LM Studio / llama.cpp / vLLM / Dify / 扣子 | OpenAI 兼容 `/chat/completions` | 共用一套 |
| 内置示例 | 无 | 只用于验证链路 |

所以代码里只有两个客户端实现。新增一个平台，只要它兼容 OpenAI 协议，
连代码都不用加，改 `AILAB_OPENAI_BASE_URL` 就行。

流式统一用"逐段产出文本"的接口（`stream()` 生成器），上层不关心底层是
NDJSON 还是 SSE，统一转成前端认的 SSE 事件。

## 四、智能体：为什么不用原生 function calling

主流做法是把工具定义发给模型，让模型返回 `tool_calls`。这对 GPT-4 级别没问题，
但本机是 **2B 级小模型**，实测有几个现实问题：

1. 很多小模型压根不支持 tool calling 协议；
2. 支持的也经常把 JSON 格式写错，一个字段名拼错整个流程就断了；
3. 调用链要来回两轮，小模型第二轮经常忘记上下文。

所以换成**两段式**：

```
用户输入 → 本地意图识别（规则） → 执行工具 → 把结果作为系统消息塞回上下文 → 模型负责组织语言
```

好处是小模型只干一件事：把已经算好的结果说人话。
计算、取时间这些事交给工具，**数字不会算错**，这是小模型最容易翻车的地方。

代价是意图识别靠关键词，覆盖面有限。这是个明确的取舍：
宁可少支持几个工具，也不要让 2B 模型去猜 JSON。

## 五、检测链路：一条"诚实降级"的路

检测后端按顺序尝试：

```
ultralytics（本机，最快）
    ↓ 不可用
远程推理服务（yolo/serve.py，可放到有显卡的机器）
    ↓ 不可用
返回 engine="none" + 解释
```

关键在最后一步。**"没有模型"也是一个合法的结果**，要如实告诉用户，
而不是编一个看起来像检测结果的东西出来。

前端在这个基础上加了一层浏览器端降级：局部对比度 + 连通域找显著区域，
把大致"有东西的地方"框出来。它有两个作用：

1. 没有模型的机器上，也能验证"上传 → 接口 → 画框"这条链路是通的；
2. 帮用户判断框的位置对不对，提前发现坐标缩放写反这类问题。

界面上它被标注为"启发式演示"，`engine` 字段也和真实推理区分开。
**演示可以降级，但不能冒充。**

推理服务单独拆成 `yolo/serve.py` 是同一个思路：ultralytics 依赖 torch，
把它和零依赖的主应用隔开，两边可以部署在不同的机器上，用 HTTP 说话。

## 六、坐标和缩放：一个容易踩的坑

检测框是原图坐标，但显示时图片被缩放过，还叠加了屏幕的 DPI 缩放。
处理方式是分两层：

- canvas 内部像素 = 显示尺寸 × `devicePixelRatio`（保证高清屏不糊）；
- 画框时把原图坐标乘以 `fitScale`（保证框对得准）。

这两件事分开算，才不会出现"框整体偏移"或"框大小差一倍"。

## 七、桌面端：为什么不直接上 Electron 打包

Electron 能打包，但需要 `npm install`（几百 MB）和构建步骤。
在装不了依赖的环境里，这条路是走不通的。

所以给了两条路：

| 方式 | 依赖 | 适用 |
| --- | --- | --- |
| `desktop/run_desktop.py` | 零依赖，调用系统已有的 Edge/Chrome | 演示、验收 |
| `desktop/electron/` | 需要 npm install | 真正要发给别人用的桌面程序 |

前者用浏览器的 `--app=` 参数，没有地址栏和标签页，视觉上已经是桌面应用；
后者负责"产品化"，代码也已经写好，能联网的机器上 `npm start` 即可。

## 八、8G 显存怎么分配

显卡是 RTX 4060 / 8 GB，要在上面同时考虑大模型和 YOLO：

| 用途 | 选择 | 显存 |
| --- | --- | --- |
| 大模型 | `qwen2.5:1.5b`（Q4） | 约 1.5 ~ 2.5 GB |
| 目标检测 | `yolo11n.pt` @ 640 | 约 1.5 GB |
| 训练 | `yolo11n` + batch 8 + AMP | 约 4 ~ 6 GB |

结论是：**推理可以同时跑，训练时先把大模型停掉。**
详细数字和调参建议写在 `docs/模型部署与显存规划.md`。

## 九、怎么保证"我这边能跑，你那边也能跑"

不靠嘴上说，靠一个能重复执行的脚本：

`tools/smoke_test.py` 会自己拉起服务，依次访问所有接口，覆盖正常路径和错误分支，
最后打印通过/失败统计。它不依赖任何第三方库，任何机器上都能跑。

这样做的意义是：**换了环境出问题，先跑一遍它**，就能快速区分
是环境问题还是代码问题，不用靠猜。

## 十、没做/做不到的事情，以及怎么处理

说清楚边界也是一种负责。下面每条都写了"为什么卡住"和"后来怎么办"：

| 事项 | 卡在哪 | 怎么处理 |
| --- | --- | --- |
| 用 coco8 等官方数据集 | 这台机器访问 github.com 证书校验失败 | 自己写脚本生成合成数据集，标注格式与真实数据集一致 |
| 用预训练权重做迁移学习 | 权重文件同样托管在 GitHub | 改用 `--model yolo11n.yaml` 从零训练，100 轮后指标正常 |
| 用显卡训练 YOLO | CUDA 版 torch 2.6 GB，单连接只有 0.9 MB/s | 写了多线程分段下载工具，15 分钟下完，训练切到 RTX 4060 |
| 用自己训练的模型检测真实照片 | 训练集是合成的，模型只认合成风格 | 应用演示改用 COCO 预训练权重，自己训练的权重只用于验证训练流程 |
| 在真实道路数据上评测 | 没有真实数据集，也没有标注人力 | 指标只在合成集上成立，已在训练记录里明确标为局限 |
| 用户系统、鉴权、会话持久化 | —— | 单机作业项目，不做，属于过度设计 |

### 一个值得记下来的教训

30 轮的模型 mAP50 有 0.888，看起来已经能交差。但它输出的**置信度普遍只有 0.1 左右**，
拿到应用里几乎检不出东西；加到 100 轮，指标和置信度才同时正常。

**指标好看不等于能用。** 如果当时只看 mAP 就收工，交上去一跑就会露馅。

### 第二个教训：合成数据训出来的模型，是真的不能用

把示例图换成真实照片之后，自己训练的模型几乎什么都检不出来——0.995 的 mAP
在真实场景面前完全没有意义。

这不是 bug，是**数据分布不匹配**的必然结果。教训有两条：

1. 评估指标必须和"打算在什么场景用"对齐，合成集上的高分说明不了别的；
2. **不要用假输入验证真系统**。之前用程序画的卡通图做演示，一路都是绿的；
   换成真实照片，问题立刻就出来了。
